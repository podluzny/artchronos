## Детальные описания

### SC-AUTH-001 — Пользователь входит в систему
* **Actor:** любой пользователь (в примере — Admin).
* **Preconditions:** учетная запись `ACTIVE`, пароль установлен, нет активной блокировки.
* **Trigger:** пользователь открывает административный интерфейс.
* **Main flow:** 1) система показывает форму входа; 2) пользователь вводит email и пароль; 3) система проверяет учетные данные и статус; 4) создается новая сессия (новый id); 5) формируется authorization context; 6) пользователь видит навигацию, соответствующую его правам; 7) событие входа журналируется.
* **Alternative flows:** A1 неверные данные → общее сообщение «Неверный email или пароль», счетчик неудач++ ; A2 статус `BLOCKED`/`ARCHIVED`/`INVITED` → то же общее сообщение, аудит с причиной; A3 `mustChangePassword` → переход к смене пароля до доступа к ресурсам.
* **Business rules:** BR-014, BR-035.
* **Expected result:** аутентифицированная сессия; навигация по правам; запись аудита.

### SC-AUTH-002 — Выход / истечение сессии
* **Actor:** любой. **Preconditions:** активная сессия. **Trigger:** «Выйти» или неактивность > idle timeout.
* **Main flow:** 1) пользователь нажимает «Выйти»; 2) сессия отзывается на сервере; 3) cookie очищается; 4) переход на вход.
* **Alternative flows:** A1 истек idle/absolute timeout → следующий запрос перенаправляется на вход, несохраненный черновик формы не теряется на сервере (последнее сохранение); A2 сессия отозвана из-за блокировки/смены пароля → то же.
* **Business rules:** BR-014. **Expected result:** сессия недействительна, повторное использование cookie невозможно.

### SC-AUTH-003 — Временная блокировка при подборе
* **Actor:** внешний нарушитель. **Preconditions:** известен email. **Trigger:** серия неверных паролей.
* **Main flow:** 1) 5 неудач подряд; 2) учетная запись блокируется для входа на 15 минут; 3) ответы остаются идентичными «неверный email или пароль»; 4) события журналируются.
* **Alternative flows:** A1 верный пароль во время блокировки → отказ; A2 после истечения — вход возможен, счетчик сброшен после успеха.
* **Business rules:** —. **Expected result:** подбор неэффективен, нет утечки информации о существовании email.

### SC-AUTH-004 — Смена и сброс пароля
* **Actor:** пользователь; Admin. **Preconditions:** активная сессия / право `user.password.reset`.
* **Trigger:** пользователь меняет пароль в профиле; Admin инициирует сброс.
* **Main flow:** 1) пользователь вводит текущий и новый пароль; 2) проверка политики; 3) сохранение hash; 4) прочие сессии отзываются; 5) аудит.
* **Alternative flows:** A1 Admin сбрасывает: генерируется одноразовая ссылка (TTL 1 ч), `mustChangePassword=true`, сессии пользователя отзываются; A2 слабый пароль → ошибка с требованиями.
* **Business rules:** BR-014, BR-035. **Expected result:** новый пароль действует, старые сессии недействительны.

### SC-USER-001 — Администратор создает студента
* **Actor:** Admin. **Preconditions:** `user.create`. **Trigger:** новый студент курса.
* **Main flow:** 1) Admin создает пользователя: email, имя; 2) выбирает роль `STUDENT`; 3) (опционально) добавляет в группу; 4) система создает пользователя в `INVITED` и ссылку активации; 5) аудит.
* **Alternative flows:** A1 email уже существует → ошибка; A2 Admin задает временный пароль → статус `ACTIVE`, `mustChangePassword=true`.
* **Business rules:** BR-035. **Expected result:** пользователь существует, может активировать аккаунт и войти.

### SC-USER-002 — Назначение роли
* **Actor:** Admin. **Preconditions:** `user.role.assign`. **Trigger:** преподаватель становится и экспертом.
* **Main flow:** 1) Admin открывает пользователя; 2) добавляет роль `EXPERT`; 3) система сохраняет `UserRole` (grantedBy); 4) аудит (до/после); 5) права действуют со следующего запроса пользователя.
* **Alternative flows:** A1 Admin пытается изменить свои роли → отказ (BR-015); A2 снятие `ADMIN` у последнего администратора → отказ (BR-016).
* **Business rules:** BR-015, BR-016, BR-035. **Expected result:** роль назначена, журнал содержит запись.

### SC-USER-003 — Блокировка пользователя
* **Actor:** Admin. **Preconditions:** `user.status.manage`. **Trigger:** нарушение правил / отчисление.
* **Main flow:** 1) Admin выбирает «Заблокировать», указывает причину; 2) статус `BLOCKED`; 3) все сессии пользователя отзываются; 4) аудит.
* **Alternative flows:** A1 блокировка себя → отказ (BR-015); A2 последний Admin → отказ (BR-016); A3 «Разблокировать» → `ACTIVE`.
* **Business rules:** BR-014, BR-015, BR-016. **Expected result:** пользователь не может войти; его контент сохраняется.

### SC-PERM-001 — Изменение состава роли
* **Actor:** Admin. **Preconditions:** `role.manage`. **Trigger:** нужно дать преподавателям право публикации.
* **Main flow:** 1) Admin открывает роль `TEACHER`; 2) добавляет `test.publish` со scope `ANY`; 3) сохраняет; 4) аудит до/после.
* **Alternative flows:** A1 scope не поддерживается permission → ошибка валидации; A2 удаление системной роли → отказ (BR-046).
* **Business rules:** BR-046, BR-035. **Expected result:** изменения действуют для всех пользователей роли.

### SC-EDU-001 — Ведение тем и учебных целей
* **Actor:** Teacher. **Preconditions:** преподаватель курса, `taxonomy.manage` (COURSE).
* **Trigger:** подготовка курса «Искусство Возрождения».
* **Main flow:** 1) создает тему «Высокое Возрождение» и подтему «Леонардо да Винчи»; 2) задает порядок; 3) добавляет учебные цели к подтеме; 4) аудит.
* **Alternative flows:** A1 попытка удалить используемую тему → предложение архивировать (BR-042); A2 тема чужого курса → отказ.
* **Business rules:** BR-042. **Expected result:** структура курса доступна для заданий и классификации контента.

### SC-EDU-002 — Формирование группы
* **Actor:** Teacher. **Preconditions:** `group.manage` (COURSE). **Trigger:** новый поток студентов.
* **Main flow:** 1) создает группу «ИИ-21»; 2) добавляет студентов (поиск по пользователям курса/email); 3) аудит.
* **Alternative flows:** A1 пользователь без роли STUDENT → предупреждение, добавление запрещено.
* **Business rules:** BR-035. **Expected result:** группа может быть адресатом задания.

### SC-ASSIGN-001 — Преподаватель создает задание
* **Actor:** Teacher. **Preconditions:** `assignment.create` в курсе; есть темы, цели, группа.
* **Trigger:** учебный план требует, чтобы студенты составили тест по теме.
* **Main flow:** 1) создает задание в курсе; 2) задает название, инструкции; 3) выбирает темы и учебные цели; 4) выбирает допустимые типы вопросов; 5) задает minItems/maxItems, maxTestsPerStudent; 6) задает дедлайн; 7) выбирает адресатов (группа и/или студенты); 8) reviewer по умолчанию = он сам; 9) сохраняет (`DRAFT`); 10) активирует (`ACTIVE`).
* **Alternative flows:** A1 активация без адресатов/тем/типов → ошибка; A2 выбран неактивный тип → ошибка; A3 reviewer по умолчанию — другой преподаватель с `review.perform`.
* **Business rules:** BR-043, BR-027, BR-018. **Expected result:** студенты-адресаты видят активное задание.

### SC-ASSIGN-002 — Ведение задания
* **Actor:** Teacher. **Preconditions:** задание существует, owner.
* **Trigger:** контроль хода выполнения.
* **Main flow:** 1) открывает задание; 2) видит сводку по студентам: тест создан?, состояние последней версии; 3) после окончания закрывает задание (`CLOSED`).
* **Alternative flows:** A1 reopen закрытого (аудит); A2 архивирование закрытого.
* **Business rules:** BR-017, BR-031. **Expected result:** после закрытия новые тесты/вопросы и отправки невозможны.

### SC-ASSIGN-003 — Продление дедлайна
* **Actor:** Teacher. **Preconditions:** owner задания, задание `ACTIVE`.
* **Trigger:** уважительная причина студента.
* **Main flow:** 1) выбирает студента; 2) задает новую дату; 3) `DeadlineExtension` сохраняется, аудит.
* **Alternative flows:** A1 дата раньше общего дедлайна → ошибка.
* **Business rules:** BR-031. **Expected result:** студент может отправить первую версию до новой даты.

### SC-MEDIA-001 — Создание media asset с metadata
* **Actor:** Student/Teacher. **Preconditions:** `media.upload`.
* **Trigger:** нужен образ произведения для вопроса.
* **Main flow:** 1) загружает файл; 2) система проверяет тип/размер, вычисляет sha256; 3) пользователь заполняет title, alt text, сведения о произведении, источник, лицензию; 4) сохраняет; 5) `rightsStatus = PENDING`; 6) превью генерируются асинхронно; 7) аудит.
* **Alternative flows:** A1 недопустимый формат/размер → ошибка; A2 дубликат по sha256 → предложение использовать существующий; A3 пользователь без `media.rights.manage` пытается выставить `CLEARED` → поле недоступно, сервер отклоняет.
* **Business rules:** BR-045. **Expected result:** медиа доступно в медиа-пикере; в черновиках можно использовать.

### SC-MEDIA-002 — Права, использование, архив
* **Actor:** Teacher. **Preconditions:** `media.rights.manage`.
* **Trigger:** медиа нужно для отправки вопроса на экспертизу.
* **Main flow:** 1) открывает медиа в `PENDING`; 2) проверяет источник/лицензию; 3) заполняет rightsHolder/creditLine; 4) ставит `CLEARED`; 5) аудит.
* **Alternative flows:** A1 обязательные поля для `CLEARED` пусты → ошибка; A2 ставит `RESTRICTED` → система показывает использование, включая опубликованные тесты; A3 архивирование используемого медиа → разрешено (новые ссылки запрещены, BR-039), удаление → отказ (BR-026).
* **Business rules:** BR-024, BR-026, BR-039, BR-045. **Expected result:** статус прав установлен; видно, где медиа используется.

### SC-MEDIA-003 — Поиск в медиатеке
* **Actor:** любой с `media.read`. **Main flow:** 1) фильтр по тексту (title, artist, workTitle), тегам, теме, статусу прав, типу; 2) сетка превью; 3) открытие карточки. **Alternative flows:** A1 архивированные скрыты по умолчанию. **Expected result:** нужное медиа найдено.

### SC-QTYPE-001 — Создание configurable type
* **Actor:** Admin. **Preconditions:** `qtype.manage`.
* **Trigger:** нужен тип «Атрибуция по фрагменту».
* **Main flow:** 1) создает тип: code, название; 2) выбирает interaction `choice` из списка плагинов; 3) задает конфигурацию (stimulus обязателен, single, 3–6 вариантов); 4) выбирает evaluator `exact`; 5) система валидирует конфигурацию по configSchema плагина и создает `QuestionTypeVersion` v1; 6) активирует тип; 7) аудит.
* **Alternative flows:** A1 невалидная конфигурация → ошибки по полям; A2 code занят → ошибка.
* **Business rules:** BR-022, BR-023. **Expected result:** тип доступен для новых вопросов (и для выбора в заданиях).

### SC-QTYPE-002 — Изменение / деактивация типа
* **Actor:** Admin. **Main flow:** 1) меняет конфигурацию → новая `QuestionTypeVersion` vN+1; существующие вопросы остаются на своей версии; 2) деактивирует тип → недоступен для новых вопросов. **Alternative flows:** A1 тип входит в allowed активных заданий → предупреждение со списком заданий. **Business rules:** BR-021, BR-022. **Expected result:** существующий контент не затронут.

### SC-ITEM-001 — Студент создает вопрос single choice
* **Actor:** Student. **Preconditions:** авторизован, `item.create`, активное задание адресовано ему, `single_choice` разрешен заданием.
* **Trigger:** выполнение задания.
* **Main flow:** 1) «Создать вопрос» из задания; 2) выбирает тип (список ограничен allowed); 3) система загружает schema типа; 4) показывает форму: формулировка, варианты, отметка верного, тема/цели (из задания), сложность, баллы; 5) студент заполняет; 6) система валидирует; 7) создается `Item` (owner = студент, assignmentId) и `ItemVersion` v1 `DRAFT`; 8) аудит.
* **Alternative flows:** A1 нет верного варианта / меньше 2 вариантов → черновик сохраняется с предупреждениями, submit невозможен; A2 тип не разрешен → недоступен в списке, прямой запрос отклоняется (BR-018); A3 задание закрыто → отказ (BR-017).
* **Business rules:** BR-017, BR-018, BR-019, BR-020, BR-021. **Expected result:** черновик вопроса принадлежит студенту.

### SC-ITEM-002 — Вопрос с вариантами-изображениями
* **Actor:** Student. **Preconditions:** как SC-ITEM-001, тип `image_choice` разрешен.
* **Main flow:** 1) выбирает `image_choice`; 2) для каждого варианта выбирает MediaAsset в медиа-пикере (или загружает новый — SC-MEDIA-001); 3) задает alt text (если у медиа нет); 4) отмечает верный; 5) сохраняет черновик.
* **Alternative flows:** A1 медиа `PENDING` → допускается в черновике с предупреждением «до отправки права должны быть подтверждены»; A2 медиа `RESTRICTED` или архивировано → выбор запрещен; A3 нет alt text → предупреждение, блокирует submit.
* **Business rules:** BR-024, BR-025, BR-039. **Expected result:** черновик с вариантами-изображениями.

### SC-ITEM-003 — Редактирование черновика
* **Actor:** автор. **Preconditions:** версия `DRAFT`, автор = owner.
* **Main flow:** 1) открывает черновик; 2) изменяет; 3) сохраняет (revision++); 4) аудит (diff).
* **Alternative flows:** A1 версия не DRAFT → действие «Редактировать» недоступно, прямой запрос отклонен, предлагается «Создать новую версию»; A2 конфликт revision (открыто в двух вкладках) → ошибка конфликта, данные не теряются; A3 чужой черновик → 404.
* **Business rules:** BR-004, BR-006, BR-007. **Expected result:** изменения сохранены только в черновике.

### SC-ITEM-004 — Preview вопроса
* **Actor:** автор / reviewer. **Main flow:** 1) «Предпросмотр»; 2) вопрос отображается как для студента (с перемешиванием вариантов по seed); 3) пользователь отвечает; 4) система показывает оценку evaluator'ом и правильный ответ. **Alternative flows:** A1 невалидный черновик → preview с перечнем ошибок. **Business rules:** —. **Expected result:** автор и эксперт проверяют работу вопроса.

### SC-ITEM-005 — Поиск в банке вопросов
* **Actor:** Teacher. **Main flow:** 1) список вопросов (по scope: свои, своих заданий, курсов); 2) фильтры: тип, тема, цель, тег, сложность, состояние, автор, задание; 3) drawer с preview выбранного вопроса и историей версий. **Alternative flows:** A1 студент видит только свои вопросы. **Business rules:** BR-004 (scope). **Expected result:** найден нужный вопрос.

### SC-ITEM-006 — Самостоятельная экспертиза вопроса банка
* **Actor:** Teacher. **Main flow:** 1) «Отправить на экспертизу» для своего черновика; 2) полная валидация (schema, alt, права); 3) версия → `READY_FOR_REVIEW`; 4) создается Review, назначается reviewer (выбор автора из допустимых, по умолчанию — Admin-очередь). **Alternative flows:** A1 ошибки валидации → список. **Business rules:** BR-020, BR-024, BR-025, BR-027. **Expected result:** вопрос в очереди экспертизы.

### SC-ITEM-007 — Архивирование / восстановление вопроса
* **Actor:** owner, Admin. **Main flow:** 1) «Архивировать» с причиной; 2) Item → `ARCHIVED`; черновик → ARCHIVED; 3) вопрос исчезает из поиска для новых тестов; существующие тесты не затронуты; 4) аудит; 5) «Восстановить» → `ACTIVE`. **Alternative flows:** A1 студент архивирует вопрос, входящий в отправленный тест другого автора → отказ. **Business rules:** BR-005, BR-039. **Expected result:** контент не удаляется физически.

### SC-TEST-001 — Студент создает тест из задания
* **Actor:** Student. **Preconditions:** активное задание адресовано студенту; лимит тестов не исчерпан.
* **Main flow:** 1) открывает задание; 2) «Создать тест»; 3) вводит название, описание; 4) создается `Test` (owner, assignmentId, courseId) и `TestVersion` v1 `DRAFT` с одним разделом по умолчанию; 5) аудит.
* **Alternative flows:** A1 лимит исчерпан → отказ (BR-033); A2 задание закрыто/не адресовано → отказ (BR-017).
* **Business rules:** BR-017, BR-033. **Expected result:** черновик теста, привязанный к заданию.

### SC-TEST-002 — Разделы и фиксированные вопросы
* **Actor:** автор. **Preconditions:** черновик теста.
* **Main flow:** 1) добавляет раздел(ы), инструкции; 2) добавляет вопросы: из своих вопросов (студент) или из банка (преподаватель); 3) создает новый вопрос прямо из теста (SC-ITEM-001, вопрос сразу добавляется); 4) задает баллы и порядок; 5) сохраняет.
* **Alternative flows:** A1 добавление чужого неутвержденного вопроса → отказ (BR-011); A2 один Item дважды → отказ; A3 архивированный Item → отказ (BR-039).
* **Business rules:** BR-010, BR-011, BR-039. **Expected result:** структура теста с pinned ItemVersion.

### SC-TEST-003 — Правило случайного отбора
* **Actor:** Teacher. **Preconditions:** `test.random_selection`.
* **Main flow:** 1) в разделе «Добавить случайный отбор»; 2) задает фильтр (темы, теги, типы, сложность) и количество; 3) система показывает текущий размер пула; 4) задает баллы за вопрос; 5) сохраняет.
* **Alternative flows:** A1 пул < count → предупреждение в черновике, блокирует submit/approve (BR-012).
* **Business rules:** BR-012. **Expected result:** раздел с правилом отбора.

### SC-TEST-004 — Настройки теста
* **Actor:** автор. **Main flow:** задает лимит времени, навигацию, попытки, перемешивание, режим обратной связи, проходной балл; система показывает maxScore. **Alternative flows:** A1 passingScore > maxScore → ошибка. **Expected result:** настройки сохранены в черновике.

### SC-TEST-005 — Отправка на экспертизу
* **Actor:** автор. **Preconditions:** черновик; до дедлайна (для первой отправки).
* **Main flow:** 1) «Отправить на экспертизу»; 2) система выполняет проверку готовности: структура, ограничения задания, валидность вопросов, alt text, права медиа, пулы; 3) показывает итог; 4) автор подтверждает; 5) TestVersion и собственные DRAFT-вопросы → `READY_FOR_REVIEW` (заморозка); 6) создается Review и ReviewAssignment на reviewer по умолчанию; 7) уведомление reviewer (в очереди); 8) аудит.
* **Alternative flows:** A1 ошибки готовности → список с переходом к месту ошибки, отправка не выполняется; A2 дедлайн прошел → отказ (BR-031); A3 автор «Отозвать отправку» до начала review → `DRAFT` (BR-038); после начала review → недоступно.
* **Business rules:** BR-007, BR-020, BR-024, BR-025, BR-031, BR-032, BR-038. **Expected result:** версия заморожена и в очереди эксперта.

### SC-TEST-006 — Preview теста
* **Actor:** автор / reviewer. **Main flow:** просмотр теста как для студента с выбором seed для случайных разделов; отображение maxScore, времени. **Expected result:** проверка восприятия теста.

### SC-REVIEW-001 — Преподаватель получает тест на экспертизу
* **Actor:** Teacher (reviewer по умолчанию). **Preconditions:** тест отправлен.
* **Main flow:** 1) в очереди «Мои экспертизы» появляется Review (тест, автор, задание, дата отправки); 2) открывает; 3) «Начать экспертизу» → версия `IN_REVIEW`; 4) видит preview, checklist, вопросы пакета.
* **Alternative flows:** A1 reviewer оказался соавтором → назначение было бы отклонено (BR-027), Review назначается owner'у задания вручную; A2 reviewer заблокирован → Admin переназначает.
* **Business rules:** BR-001, BR-027. **Expected result:** экспертиза начата.

### SC-REVIEW-002 — Эксперт возвращает тест на доработку
* **Actor:** primary reviewer. **Preconditions:** `IN_REVIEW`.
* **Main flow:** 1) оставляет комментарии к тесту, разделу, конкретному вопросу/полю; 2) часть комментариев отмечает как замечания (ContentIssue) с severity; 3) пишет итоговый summary; 4) «Вернуть на доработку»; 5) версия и вопросы пакета → `CHANGES_REQUESTED`; Review закрыт; 6) автор видит замечания; 7) аудит.
* **Alternative flows:** A1 нет ни одного замечания и summary → отказ (BR-029); A2 попытка от не-primary → отказ (BR-030).
* **Business rules:** BR-001, BR-029, BR-030, BR-040. **Expected result:** автор получил замечания; версия неизменна.

### SC-REVIEW-003 — Эксперт принимает тест
* **Actor:** primary reviewer. **Preconditions:** `IN_REVIEW`.
* **Main flow:** 1) отмечает все обязательные пункты checklist; 2) проверяет, что блокирующие замечания закрыты; 3) «Принять»; 4) система проверяет BR-001, BR-011, BR-012, BR-024, BR-028; 5) TestVersion и вопросы пакета → `APPROVED`; пулы заморожены; 6) аудит.
* **Alternative flows:** A1 не все обязательные пункты → отказ со списком; A2 открытые BLOCKING замечания → отказ; A3 reviewer — автор (например, Admin, назначивший себя на свой тест) → отказ (BR-001); A4 медиа потеряло `CLEARED` за время review → отказ со списком.
* **Business rules:** BR-001, BR-011, BR-012, BR-024, BR-028. **Expected result:** версия утверждена и immutable.

### SC-REVIEW-004 — Переназначение и advisory
* **Actor:** owner задания / Admin. **Main flow:** 1) открывает Review; 2) заменяет primary reviewer (предыдущее назначение → REVOKED) или добавляет advisory; 3) система проверяет BR-027; 4) аудит. **Alternative flows:** A1 кандидат — автор → отказ. **Business rules:** BR-027, BR-030. **Expected result:** новый эксперт видит Review в очереди.

### SC-REVIEW-005 — Замечания между версиями
* **Actor:** Student, Expert. **Main flow:** 1) студент создает новую версию (SC-VERSION-001); 2) незакрытые замечания предыдущего review связаны с новой версией; 3) студент исправляет и отмечает замечания «устранено» (ADDRESSED) с комментарием; 4) после повторной отправки эксперт видит замечания со ссылкой на изменения (diff); 5) закрывает (RESOLVED) или переоткрывает (OPEN). **Alternative flows:** A1 студент не согласен → WONT_FIX может поставить только reviewer. **Business rules:** BR-028. **Expected result:** прослеживаемость замечаний между версиями.

### SC-REVIEW-006 — Шаблоны checklist
* **Actor:** Admin. **Main flow:** создает/изменяет шаблон, отмечает обязательные пункты; изменения влияют только на новые Review. **Expected result:** актуальный checklist.

### SC-VERSION-001 — Студент изменяет тест после замечаний
* **Actor:** Student. **Preconditions:** версия `CHANGES_REQUESTED`; задание не `CLOSED`.
* **Main flow:** 1) открывает тест, видит замечания; 2) «Создать новую версию» → TestVersion v2 `DRAFT` (копия, basedOn v1); 3) для собственных вопросов пакета в `CHANGES_REQUESTED` система создает новые DRAFT-версии и ссылается на них в v2 (SPEC-TEST-004); 4) исправляет; 5) отмечает замечания ADDRESSED; 6) отправляет v2 (SC-TEST-005).
* **Alternative flows:** A1 черновик уже существует → открывается он (BR-041); A2 задание закрыто → отказ (BR-031).
* **Business rules:** BR-003, BR-007, BR-031, BR-041. **Expected result:** v1 неизменна, v2 в экспертизе.

### SC-VERSION-002 — Новая версия утвержденного вопроса
* **Actor:** Teacher. **Main flow:** 1) на утвержденном вопросе «Создать новую версию»; 2) редактирует; 3) отправляет на экспертизу; 4) после утверждения новая версия доступна для новых тестов; 5) старые тесты не меняются; 6) сравнение версий. **Business rules:** BR-003, BR-006, BR-010. **Expected result:** две утвержденные версии; тесты ссылаются на свои.

### SC-PUBLISH-001 — Публикация approved version
* **Actor:** Admin. **Preconditions:** `test.publish`; TestVersion `APPROVED`; Test `ACTIVE`.
* **Main flow:** 1) открывает утвержденную версию; 2) «Опубликовать», подтверждение; 3) версия → `PUBLISHED`; предыдущая опубликованная → `ARCHIVED (SUPERSEDED)`; 4) `Test.publishedVersionId`; 5) аудит; 6) запись в истории публикаций.
* **Alternative flows:** A1 версия не APPROVED → действие недоступно, прямой запрос отклонен (BR-008).
* **Business rules:** BR-008, BR-009. **Expected result:** у теста ровно одна опубликованная версия.

### SC-PUBLISH-002 — Отзыв публикации
* **Actor:** Admin. **Main flow:** «Отозвать» с причиной → `ARCHIVED (WITHDRAWN)`, publishedVersionId = null, аудит. **Alternative flows:** A1 без причины → ошибка. **Business rules:** BR-036. **Expected result:** новые попытки невозможны; прежние данные сохранены.

### SC-PUBLISH-003 — Архивирование теста
* **Actor:** owner/Admin. **Main flow:** «Архивировать» → Test `ARCHIVED`; черновики → ARCHIVED; «Восстановить» → `ACTIVE`. **Alternative flows:** A1 есть опубликованная версия → сначала отзыв. **Business rules:** BR-005, BR-039. **Expected result:** тест скрыт из рабочих списков, данные сохранены.

### SC-AUDIT-001 — Расследование по журналу
* **Actor:** Admin. **Main flow:** фильтр журнала по пользователю/ресурсу/действию/периоду; просмотр записи с diff. **Alternative flows:** A1 попытка изменить/удалить запись → действия отсутствуют, прямой запрос отклонен. **Business rules:** BR-034. **Expected result:** установлено, кто и когда изменил объект.

### SC-AUDIT-002 — История объекта
* **Actor:** любой с правом чтения объекта. **Main flow:** вкладка «История» у вопроса/теста/задания: события с авторами и датами. **Expected result:** прозрачная история.

### SC-AUDIT-003 — Архивирование/восстановление с журналированием
* **Actor:** owner, Admin. **Main flow:** любой ресурс с soft delete: «Архивировать» (причина) → скрыт из рабочих списков; фильтр «Показать архив»; «Восстановить». **Business rules:** BR-005, BR-039, BR-042. **Expected result:** единообразное поведение.

## SC-E2E-001 — E2E reference scenario (T-028)

Сквозной сценарий, проверяющий большую часть архитектуры. Автоматизируется Playwright-тестом `AT-E2E-001` и
дублируется сервисным тестом без UI `AT-E2E-001-API` (проверка, что сценарий работает без UI).

**Начальные данные (seed):** Admin `admin@`, курс «История русского искусства», тема «Пейзаж XIX века»
с целью «Атрибутировать произведение по стилю», активные типы MVP, шаблоны checklist; 3 изображения с `CLEARED`.
