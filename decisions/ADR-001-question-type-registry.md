# ADR-001: Хранение QuestionType и schema

| Поле | Значение |
|---|---|
| Статус | Accepted (T-030, 2026-10-08) |
| Дата | 2026-10-08 |
| Задача | T-014 |
| Связанные требования | FR-QTYPE-001…006, NFR-EXT-001, NFR-EXT-002, BR-020…BR-023, INV-015 |

## Контекст
Нужно поддерживать расширяемый набор типов вопросов. Администраторы хотят создавать варианты типов без
разработки (например, «атрибуция» = выбор с обязательным изображением-стимулом). При этом принципиально
новое взаимодействие (hotspot, drag-and-drop) требует UI-кода, валидации и алгоритма оценивания, которые
нельзя безопасно задать данными. Ввод произвольного кода через AdminJS недопустим (безопасность, сопровождаемость).

## Решение
**Configuration-driven registry + code-level interaction plugins.**

1. В коде существует реестр `InteractionPlugin` (ключ → реализация). Плагин объявляет:
   `key`, `configSchema` (допустимая конфигурация), `baseContentSchema`, `responseSchema`, список `evaluators`,
   функцию `buildContentSchema(config)`, `validate(version)`, `evaluate(version, response, evaluatorParams)`,
   компоненты AdminJS `Editor`, `Preview`, и описание ролей `ItemOption`.
2. В БД `QuestionType` (code, name, interactionKey, status) и неизменяемые `QuestionTypeVersion`
   (interactionConfig, contentSchema = baseContentSchema ⊕ ограничения, responseSchema, evaluation).
3. AdminJS позволяет создать/изменить configurable type, выбирая `interactionKey` только из реестра;
   конфигурация валидируется `configSchema` плагина. Изменение = новая `QuestionTypeVersion`.
4. Seed-миграция создает MVP-типы (question-type-system.md §3).

## Рассмотренные альтернативы
| Вариант | Плюсы | Минусы | Почему отклонен |
|---|---|---|---|
| Таблица на каждый тип вопроса | Строгая реляционная модель | Новый тип = миграция БД; нарушает NFR-EXT-001 | Расширяемость |
| Полностью data-driven (UI и оценивание из конфигурации/скриптов) | Без деплоя | Исполнение произвольного кода, невозможность тестирования, XSS | Безопасность (BR-023) |
| Только код (типы захардкожены) | Простота | Каждая вариация — разработка | Не покрывает потребность в конфигурации |

## Последствия
* Новый interaction — задача разработки с contract-тестами плагина; новый configurable type — операция администратора.
* Плагин обязан поддерживать все используемые версии своей конфигурации.
* Редактор вопроса в AdminJS — общий компонент-оболочка, загружающий `Editor` плагина по `interactionKey`.

## Верификация
* Contract test suite, запускаемый для каждого зарегистрированного плагина (NFR-EXT-002).
* AT: создание типа с несуществующим interactionKey отклоняется (AT-QTYPE-001.2).
* AT: добавление тестового плагина-фикстуры не требует миграции (AT-QTYPE-002.2).
