# ADR-006: Authentication mechanism

| Поле | Значение |
|---|---|
| Статус | Accepted (T-030, 2026-10-08) |
| Дата | 2026-10-08 |
| Задача | T-011 |
| Связанные требования | FR-AUTH-001…007, NFR-SEC-002…005, NFR-EXT-003, BR-014 |

## Контекст
AdminJS предоставляет `buildAuthenticatedRouter` с callback `authenticate(email, password)`. Аутентификация
админки не должна быть отдельной «учеткой AdminJS»: пользователи (включая студентов) — часть доменной модели,
их статусы и роли влияют на все решения. В будущем — SSO и Student Runner.

## Решение
1. Единая identity-модель: `User` домена — единственный источник учетных записей для AdminJS и будущих клиентов.
2. `@adminjs/express` `buildAuthenticatedRouter` с `authenticate`, делегирующим в `identity.AuthenticateUser` use case
   (проверка статуса, lockout, argon2id, аудит события входа).
3. Серверные сессии `express-session` с хранилищем в PostgreSQL (`connect-pg-simple` или аналог); в сессии — только
   `sessionId → userId`; actor-контекст (роли, permissions) загружается на запрос (изменение ролей действует сразу).
4. Регенерация id сессии при входе; отзыв всех сессий при блокировке/смене пароля (таблица `Session` для учета и отзыва).
5. Cookie: HttpOnly, Secure, SameSite=Lax; CSRF-защита.
6. Сброс пароля/приглашение — одноразовые токены (hash в БД, TTL). Отправка email — через порт `Mailer`
   (в MVP допускается вывод ссылки администратору, если почта не настроена).
7. Расширение: `AuthenticationProvider` порт (password сейчас, OIDC позже), привязка внешней identity к `User` через
   `UserIdentity(provider, subject)` — без изменения `User` (NFR-EXT-003).

## Рассмотренные альтернативы
| Вариант | Почему отклонен |
|---|---|
| Отдельная таблица AdminUser | Две модели пользователей, расхождение ролей |
| JWT в localStorage | Отзыв сессий сложен, XSS-риск |
| Внешний IdP с первого дня | Нет в требованиях MVP, усложняет запуск |

## Последствия
* Студенты входят в ту же админку (с урезанным набором ресурсов/действий по правам).
* Нужна таблица сессий и фоновая очистка.
