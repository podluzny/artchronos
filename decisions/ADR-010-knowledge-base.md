# ADR-010: База знаний и якоря в тексте

| Поле | Значение |
|---|---|
| Статус | Accepted |
| Дата | 2026-10-11 |
| Задача | T-088 |
| Связанные требования | FR-KB-001…FR-KB-009, BR-047…BR-051, NFR-SEC-007 |

## Контекст
BRD (10.2, 10.9, A.1) требует базу объектов истории искусства со связями. Сейчас автор, произведение, техника и собрание — свободный текст в `media_assets`. Нужны справочники, выбор из них в формах и ссылки из текста (`@slug`, `[текст](@slug)`, см. `docs/knowledge-base-audit.md`). Ограничения: неизменяемость утвержденных версий и contentHash (ADR-002), санитизация rich text (NFR-SEC-007), бизнес-логика в application layer (ADR-004).

## Решение
1. **Одна таблица `knowledge_entries`** с `kind` ∈ {PERSON, ARTWORK, COLLECTION, MOVEMENT, PERIOD, TECHNIQUE, TERM}:
   - общие колонки: `slug`, `name`, `alt_names[]`, `description`, `year_from`, `year_to`, `status`, `revision`;
   - видоспецифичные поля — в `attrs jsonb`, схема поля задается доменом (`src/domain/knowledge`);
   - связи — в `knowledge_links (from_id, to_id, relation)`, допустимые пары видов задает домен;
   - в AdminJS у каждого вида отдельный ресурс.
2. **Канонический якорь** — `[подпись](@kind:slug)`. Ввод `@slug`, `@kind:slug`, `[текст](@slug)` при сохранении нормализуется в канонический вид, подпись по умолчанию — название объекта. Подпись входит в текст, а значит в contentHash. Последующее переименование объекта не меняет сохраненный контент.
3. **Стабильность ключа:** slug уникален в пределах вида и не меняется, пока на объект есть ссылки (BR-048).
4. **`content_references (source_type, source_id, field, entry_id)`** пересобирается в той же транзакции, что и сохранение источника. Источник у вопросов и тестов — версия, поэтому ссылки замороженных версий не исчезают. Таблица обслуживает «где используется» и запрет удаления (BR-047).
5. **Отображение:**
   - в предпросмотрах после `sanitizeRichText` канонический якорь заменяется на `<span class="kb-ref" title="…">подпись</span>`;
   - подпись не может содержать `<>[]`, поэтому allow-list санитайзера не расширяется;
   - студенческое представление (`deliveryView`) выводит только подпись (BR-050).
6. **Медиа** ссылается на произведение (`artwork_id`); атрибутивные поля медиа заполняются из произведения при сохранении (BR-051).

## Рассмотренные альтернативы
| Вариант | Плюсы | Минусы | Почему отклонен |
|---|---|---|---|
| Отдельная таблица на каждый вид | Строгие колонки | 7 репозиториев и use case-наборов; разрозненный поиск и проверка якорей | Затраты без выигрыша для MVP; jsonb-поля валидируются доменом |
| Хранить в тексте id объекта (`@ref:uuid`) | Устойчив к смене slug | Нечитаемо в редакторе, нужна обратная подстановка | Заменено неизменяемостью slug при ссылках |
| Подставлять название объекта при выводе | Тексты всегда актуальны | Меняет опубликованный контент без новой версии | Нарушает ADR-002 |
| Расширить санитайзер атрибутами | Якорь как HTML в хранилище | Больше поверхность XSS | Рендер после санитизации проще и безопаснее |

## Последствия
- **Положительные:** единый поиск и ссылочная целостность; переименование не трогает утвержденный контент.
- **Отрицательные:** подпись в старом тексте не обновляется автоматически, ее правят новой версией.
- **Обязательно:** все тексты, где разрешены якоря, проходят нормализацию в application layer, а их ссылки записываются в `content_references`.
