# ADR-004: Где находится бизнес-логика

| Поле | Значение |
|---|---|
| Статус | Accepted (T-030, 2026-10-08) |
| Дата | 2026-10-08 |
| Задача | T-012 |
| Связанные требования | NFR-MAINT-001, NFR-SEC-001, NFR-EXT-005 |

## Контекст
AdminJS поощряет размещение логики в `before/after` hooks, custom actions и React-компонентах. В проекте с
десятками правил и состояний это приведет к их расползанию и невозможности повторного использования
(будущий Student Runner, API, фоновые задачи).

## Решение
1. Бизнес-правила, инварианты, state machines и политики авторизации — **только в domain/application layer**.
2. AdminJS — UI-адаптер: action handler = распаковать запрос → вызвать command/query → вернуть результат/ошибку.
   Hooks AdminJS не содержат правил (допускается только преобразование формата данных).
3. Governed-ресурсы подключаются через адаптер `DomainResource`, а не через ORM-адаптер AdminJS напрямую
   (иначе встроенные `edit/delete` обходят правила).
4. React-компоненты не принимают решений о правах/состояниях: они отображают `availableActions` и ошибки сервера.
5. Ошибки домена типизированы (`DomainError{code, ruleId, field?}`) и переводятся в сообщения UI.

## Рассмотренные альтернативы
| Вариант | Почему отклонен |
|---|---|
| Логика в AdminJS hooks/actions | Расползание правил, нет переиспользования, сложно тестировать |
| Логика в хранимых процедурах БД | Трудно тестировать и развивать; используется только для защитных триггеров (ADR-002) |

## Последствия
* Больше кода-адаптера на старте (DomainResource, маппинг ошибок).
* Domain тестируется без AdminJS и БД (быстрые unit-тесты, NFR-MAINT-003).

## Верификация
Архитектурный тест зависимостей (например, dependency-cruiser): `domain` и `application` не импортируют `adminjs`,
`@adminjs/*`, `react`, ORM-клиент; `adminjs` не импортирует ORM-клиент для governed-ресурсов.
