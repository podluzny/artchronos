# Business Rules

| Поле | Значение |
|---|---|
| Задача | T-003 |
| Статус | Draft — ожидает review (T-030) |

`FR` описывает, что система **умеет**. `BR` описывает, что системе **запрещено или обязательно**.
Нарушение BR — всегда отказ операции на сервере (domain layer), независимо от UI.

Нумерация глобальная (`BR-NNN`). Спецификации ссылаются только на эти ID.
Колонка «Enforcement» указывает, где правило проверяется: `D` — доменная модель/политика, `A` — application service (требует данных нескольких агрегатов), `DB` — дополнительно ограничение БД.

## 1. Экспертиза и авторство

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-001 | Автор (owner или соавтор) не может принять решение (approve / request changes) по собственному тесту или вопросу. Правило распространяется и на администраторов. | D | INV-003 |
| BR-027 | Reviewer назначается только из пользователей, имеющих `review.perform`, со статусом `ACTIVE`, не являющихся авторами объекта экспертизы. | A | INV-003 |
| BR-028 | Approve возможен только если: отмечены все обязательные пункты checklist; нет `ContentIssue` в статусе `OPEN` или `ADDRESSED` с severity `BLOCKING`; для TestVersion все вложенные версии вопросов могут быть утверждены (BR-011). | A | |
| BR-029 | Request changes требует хотя бы одного `ContentIssue` в статусе `OPEN` или итогового комментария (summary). | D | |
| BR-030 | В MVP у Review ровно один активный `PRIMARY` reviewer; решение принимает только он. `ADVISORY` reviewers только комментируют. | D | |
| BR-040 | После решения (`APPROVED`, `CHANGES_REQUESTED`) Review закрыт: комментарии, checklist и решение не изменяются; новые замечания возможны только в новом Review следующей версии. | D | |

## 2. Версии и неизменяемость

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-002 | После утверждения `TestVersion` не может быть изменена. | D, DB | INV-001 |
| BR-003 | Изменение утвержденного (или отправленного) теста создает новую версию (`DRAFT`, `basedOnVersionId` = исходная). | D | |
| BR-006 | После утверждения `ItemVersion` не может быть изменена; изменение создает новую `ItemVersion`. | D, DB | INV-002 |
| BR-007 | Версия становится content-frozen в момент отправки на review (`READY_FOR_REVIEW`). Дальнейшие изменения — только через новую версию. | D | INV-001, INV-002 |
| BR-038 | Автор может отозвать отправку (`READY_FOR_REVIEW → DRAFT`) только пока review не начат (нет перехода в `IN_REVIEW`). | D | |
| BR-041 | У `Test` и у `Item` одновременно существует не более одной версии в `DRAFT`. | D, DB | INV-005 |
| BR-010 | `TestVersion` ссылается на конкретные `ItemVersion` (pinning), а не на `Item`. | D | INV-006 |
| BR-019 | Тип вопроса обязателен и не меняется у `Item` между версиями. Смена типа = новый `Item`. | D | INV-009 |

## 3. Публикация и жизненный цикл

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-008 | Публиковаться может только `TestVersion` в состоянии `APPROVED`. `ItemVersion` не публикуется самостоятельно. | D | INV-004 |
| BR-009 | У `Test` одновременно не более одной `PUBLISHED` версии. Публикация новой версии переводит предыдущую в `ARCHIVED` (reason `SUPERSEDED`) в той же транзакции. | A, DB | INV-005 |
| BR-011 | `TestVersion` может быть утверждена только если все ее фиксированные вопросы ссылаются на `ItemVersion` в `APPROVED` либо утверждаются в том же решении (входят в пакет review, см. SPEC-REVIEW-003). | A | INV-007 |
| BR-012 | Пул `SelectionRule` формируется только из `APPROVED` `ItemVersion` активных `Item`; при approve `TestVersion` пул замораживается (`SelectionPoolEntry`), и его размер должен быть ≥ `count`. | A | INV-006 |
| BR-013 | Переходы состояний возможны только по state machine (`docs/lifecycle-state-machine.md`). Администратор не может обойти состояния; он может только выполнять разрешенные переходы, на которые у него есть permission. | D | |
| BR-036 | Отзыв (withdraw) опубликованной версии не удаляет и не изменяет попытки и результаты; новые попытки по ней невозможны. Отзыв требует указания причины. | A | |
| BR-037 | `Attempt` ссылается на конкретную `TestVersion`, бывшую `PUBLISHED` при старте; эта ссылка неизменна. | D | INV-012 |

## 4. Удаление и архивирование

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-005 | Hard delete опубликованного или используемого контента запрещен (Test, TestVersion, Item, ItemVersion, MediaAsset, QuestionType, Topic, LearningObjective, Assignment, User). «Удалить» в UI = архивировать. | D, DB | INV-011 |
| BR-026 | `MediaAsset`, используемый хотя бы одной не-`DRAFT` версией, не может быть удален или иметь замененный файл; замена файла всегда создает новый `MediaAsset`. | A | INV-011 |
| BR-039 | Архивированные `Item`, `MediaAsset`, `Topic`, `QuestionType` не могут добавляться в новые версии; существующие ссылки сохраняются. Восстановление из архива доступно owner (для своего контента) и Admin. | A | |
| BR-042 | Элемент учебной структуры (`Subject`, `Course`, `Topic`, `LearningObjective`), используемый контентом или заданиями, не удаляется — только архивируется. | A | |
| BR-044 | Hard delete разрешен только для `DRAFT`-версии, никогда не отправлявшейся на review и не имеющей ссылок (операция «discard draft» владельцем). Запись в AuditLog сохраняется. | A | |

## 5. Владение и задания

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-004 | Студент может редактировать только собственные `DRAFT`-объекты. | D | |
| BR-017 | Студент создает `Item` и `Test` только в рамках `ACTIVE` `Assignment`, адресованного ему (лично или через группу). | A | |
| BR-018 | Тип вопроса создаваемого в рамках задания `Item` должен входить в `Assignment.allowedQuestionTypeIds`. | A | |
| BR-031 | Отправка **первой** версии теста по заданию на review после дедлайна (с учетом персонального продления) запрещена. Повторные отправки после `CHANGES_REQUESTED` разрешены, пока `Assignment` не `CLOSED`. | A | |
| BR-032 | `TestVersion`, созданная по заданию, при отправке должна удовлетворять ограничениям задания: число вопросов в `[minItems, maxItems]` (фиксированные + count правил), все типы ∈ allowed, хотя бы одна тема задания покрыта. | A | |
| BR-033 | Студент создает не более `Assignment.maxTestsPerStudent` тестов (не архивированных) в одном задании. | A | |
| BR-043 | `Assignment` создается и ведется пользователем с `assignment.create` (Teacher, Admin); owner задания — преподаватель курса или Admin. | D | |

## 6. Типы вопросов

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-020 | Содержимое `ItemVersion` валидно по `contentSchema` своей `QuestionTypeVersion`; невалидная версия не может быть отправлена на review. Черновик может сохраняться с неполными данными (структурно валидный JSON), но полная валидация обязательна при submit. | D | INV-010 |
| BR-021 | Новые `Item` создаются только с `ACTIVE` `QuestionType`. Деактивация типа не затрагивает существующие `Item`/`ItemVersion` и их использование в тестах. | A | |
| BR-022 | `QuestionTypeVersion` неизменна после создания. Изменение конфигурации типа создает новую версию; существующие `ItemVersion` продолжают ссылаться на свою. | D | |
| BR-023 | `QuestionType` может ссылаться только на `interactionKey`, зарегистрированный в коде. Произвольный исполняемый код через AdminJS не вводится. | D | INV-015 |

## 7. Медиа

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-024 | Медиа с `rightsStatus ≠ CLEARED` не может входить в `ItemVersion`, отправляемую на review, утверждаемую или утвержденную (и, следовательно, в `APPROVED`/`PUBLISHED` `TestVersion`). В черновиках допустимо. Проверяется при submit и повторно при approve. | A | INV-007 |
| BR-025 | Изображение, используемое в вопросе, должно иметь непустой `altText` (на уровне `MediaAsset` или переопределенный в `ItemMedia`/`ItemOption`) к моменту submit. | A | |
| BR-045 | Только пользователь с `media.rights.manage` может установить `rightsStatus = CLEARED`. | D | |

## 8. Пользователи, роли, аудит

| ID | Правило | Enforcement | Инвариант |
|---|---|---|---|
| BR-014 | Пользователь в статусе `BLOCKED`, `ARCHIVED` или `INVITED` (без установленного пароля) не может аутентифицироваться; при блокировке все его сессии отзываются. | D | |
| BR-015 | Пользователь не может изменять собственные роли и permissions, а также блокировать/архивировать сам себя. | D | |
| BR-016 | Нельзя заблокировать, архивировать или лишить роли `ADMIN` последнего активного администратора. | A | INV-014 |
| BR-046 | Системные роли (`isSystem`) нельзя удалить; набор их permissions меняет только Admin, и изменение журналируется. | D | |
| BR-034 | `AuditLog` append-only: никто, включая Admin, не может изменить или удалить запись через приложение. | D, DB | INV-013 |
| BR-035 | Каждое изменение governed-ресурса, переход состояния, решение review, изменение ролей/permissions/статусов пользователя, вход/выход/неудачный вход журналируются в той же транзакции, что и изменение (кроме событий аутентификации — отдельная запись). Если запись аудита не удалась, операция откатывается. | A | |

## 9. Примечания

* BR-001…BR-005 — правила из исходного плана; номера сохранены.
* Нумерация не обязана быть непрерывной по разделам; новые правила получают следующий свободный номер (сейчас — BR-047).
* Локальные идентификаторы вида `BR-ITEM-001` в черновике плана сопоставлены глобальным:
  BR-ITEM-001 → BR-019, BR-ITEM-002 → BR-020, BR-ITEM-003 → BR-004, BR-ITEM-004 → BR-006.
