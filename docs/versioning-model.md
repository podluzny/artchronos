# Versioning Model

| Поле | Значение |
|---|---|
| Задача | T-009 |
| Статус | Draft — ожидает review (T-030) |
| Связанные | ADR-002, lifecycle-state-machine.md, SPEC-ITEM-002, SPEC-TEST-004 |

## 1. Что версионируется

| Объект | Идентичность | Версия | Почему |
|---|---|---|---|
| Вопрос | `Item` | `ItemVersion` | Экспертиза, reuse, аналитика по конкретному содержимому |
| Тест | `Test` | `TestVersion` | Экспертиза, публикация, попытки по конкретному содержимому |
| Тип вопроса | `QuestionType` | `QuestionTypeVersion` | Существующие вопросы должны оставаться валидными по своей schema |

Не версионируются (история — через AuditLog): User, Role, Subject/Course/Topic/Objective, Assignment, MediaAsset
(файл неизменен; изменение файла = новый MediaAsset; метаданные редактируемы, но поля прав после `CLEARED`
меняются только с `media.rights.manage` и журналируются).

## 2. Когда версия становится immutable

| Момент | Что фиксируется |
|---|---|
| submit (`DRAFT → READY_FOR_REVIEW`) | **Content-frozen**: содержимое версии и ее дочерних сущностей. Вычисляется `contentHash`. Единственное исключение — recall до начала review (BR-038). |
| approve (`→ APPROVED`) | **Immutable навсегда**: больше никаких переходов, кроме `PUBLISHED`/`ARCHIVED`. Для TestVersion замораживается пул случайного отбора. |

Почему заморозка при submit, а не при approve: эксперт должен комментировать стабильное содержимое;
замечания (`ContentIssue`) привязаны к версии и полям, и правки «под рецензией» сделали бы их недостоверными.

## 3. Создание новой версии

| Ситуация | Действие | Результат |
|---|---|---|
| Замечания эксперта | «Создать новую версию» на версии в `CHANGES_REQUESTED` | Новая `DRAFT`, `versionNo = max + 1`, `basedOnVersionId` = исходная; содержимое скопировано; открытые issues связаны с новой версией |
| Изменение утвержденного/опубликованного | «Создать новую версию» на `APPROVED`/`PUBLISHED` | То же; утвержденная версия и все тесты, ссылающиеся на нее, не меняются |
| Уже есть DRAFT | Отказ (BR-041) — открыть существующий черновик |  |

Копирование `ItemVersion`: `ItemOption.key` сохраняются (INV-008). Копирование `TestVersion`: разделы, фиксированные
вопросы (те же pinned `ItemVersion`), правила отбора (без замороженного пула).

## 4. Что происходит при изменении утвержденного вопроса

1. Автор создает новую `ItemVersion` (DRAFT) → проходит экспертизу → `APPROVED`.
2. **Существующие тесты не меняются**: утвержденные/опубликованные `TestVersion` продолжают ссылаться на старую `ItemVersion` (pinning, BR-010).
3. Черновики тестов **того же автора**, ссылающиеся на предыдущую версию этого `Item`, получают предложение «обновить до версии N» (не автоматически, кроме случая ниже).
4. Автоматическая перепривязка (auto-rebind): если автор создает новую `ItemVersion` из `CHANGES_REQUESTED`, и его DRAFT `TestVersion` ссылается на предыдущую версию того же `Item`, ссылка в черновике теста обновляется на новую DRAFT `ItemVersion`. Операция журналируется. Это обеспечивает сценарий доработки теста с вопросами (SC-VERSION-001).
5. Чтобы новая версия попала в опубликованный тест, нужна новая версия теста → экспертиза → публикация.
6. Пул случайного отбора утвержденной `TestVersion` заморожен; новые утвержденные вопросы в него не попадают.

## 5. Номера и указатели

* `versionNo` — последовательный в пределах `Item`/`Test`, начиная с 1, без пропусков (кроме удаленных отброшенных черновиков — BR-044).
* `Item.currentDraftVersionId`, `Item.latestApprovedVersionId`, `Test.currentDraftVersionId`, `Test.publishedVersionId` обновляются в той же транзакции, что и переход (NFR-DATA-004).

## 6. Пакет review теста

При submit `TestVersion` все `ItemVersion`, на которые она ссылается фиксированно и которые:

* принадлежат автору теста и находятся в `DRAFT` — переводятся в `READY_FOR_REVIEW` вместе с тестом (каскад);
* уже `APPROVED` — входят как есть;
* в любом другом состоянии или принадлежат другому пользователю и не `APPROVED` — submit отклоняется.

Решение по review теста применяется ко всему пакету (SPEC-REVIEW-003). Replies/issues могут адресоваться конкретному вопросу пакета.

## 7. Сравнение версий

Diff строится между любыми двумя версиями одного `Item`/`Test` по нормализованному представлению (stem, options по key,
answerKey, metadata; для тестов — разделы, pinned items, правила, настройки). FR-ITEM-008 (Should).
