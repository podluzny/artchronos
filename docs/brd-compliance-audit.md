Обозначения: ✅ выполнено · 🟡 частично или есть основа · ❌ не реализовано · ➖ вне разработки (организационное) · ⏳ не относится к текущему релизу.

## Итог

Реализован **первый релиз**: административный и авторский контур. В него входят пользователи и роли, учебная структура, задания для студентов, медиатека с учетом прав, банк вопросов, конструктор тестов, экспертиза, публикация, аудит, а также модель прохождения без интерфейса.

Это соответствует направлениям BRD **A.6 «Административная часть»** и основе **A.2 «Учебные задания»**. Студенческий контур BRD еще не реализован: выполнение заданий, личный кабинет, адаптивное обучение, повторение, прогресс и аналитика. Это ожидаемо при поэтапной реализации (BRD 8.1.1).

Оценка: соответствие **частичное**, примерно 30–35 % функционального объема BRD. Архитектура и модель данных в основном не мешают дальнейшему развитию. Есть три существенных расхождения в фундаменте:

1. **Нет базы знаний.** Художников, произведений, направлений, периодов, терминов и связей между ними (BRD 10.2, A.1) нет как самостоятельных объектов. Сведения об автор/произведение/датировке хранятся только как атрибуты медиафайла.
2. **Иначе распределены роли.** В BRD роли такие: студент, преподаватель, редактор контента, администратор. В системе: студент, преподаватель, эксперт, администратор. Роль «редактор контента» можно создать как пользовательскую, но готовой нет.
3. **Иначе понят процесс создания контента.** Система построена вокруг сценария «студенты создают тесты по заданию, эксперты их проверяют». BRD описывает тренажер: студент **выполняет** задания, подготовленные преподавателями и редакторами. Допущение BRD (раздел 9) явно говорит о создании контента студентами, так что текущий сценарий не противоречит BRD. Но это только часть его модели.

Состав MVP по BRD 8.1.2 фиксируется отдельным документом «Scope релиза 1 (MVP)». В репозитории его роль выполняет `docs/product-scope.md`. Рекомендуется согласовать его с заказчиком как официальный «Scope релиза 1».

## 2. Функциональные требования (раздел 10)

### 10.1 Управление пользователями — 🟡

| Требование | Статус | Факт |
|---|---|---|
| Регистрация | 🟡 | Самостоятельной регистрации нет. Администратор создает пользователя: по приглашению с одноразовой ссылкой или с временным паролем. Для вуза это допустимо, но с BRD нужно согласовать. |
| Аутентификация | ✅ | Вход, сессии, блокировка после неудачных попыток, смена и сброс пароля, политика паролей. |
| Разграничение прав | ✅ | RBAC с областями (свои, назначенные, курса, все), матрица прав покрыта тестами. |
| Роли «студент, преподаватель, администратор» | ✅ | Системные роли STUDENT, TEACHER, ADMIN. |
| Роль «редактор контента» | 🟡 | Готовой роли нет; есть EXPERT (экспертиза). Пользовательские роли создаются в интерфейсе («Роли»), поэтому редактора можно собрать из прав. **Рекомендация:** добавить системную роль CONTENT_EDITOR. |

### 10.2 Управление образовательным контентом — 🟡/❌

| Требование | Статус | Факт |
|---|---|---|
| Исторические периоды | 🟡 | Можно моделировать темами (Topic) с иерархией; отдельной сущности с датировкой нет. |
| Художественные направления | 🟡 | Так же: темой или тегом. |
| Художники, произведения, архитектура, скульптура | ❌ | Только текстовые поля медиа: `artist`, `workTitle`, `dateText`, `technique`, `collection`. Одно произведение с двумя фото — два несвязанных объекта. |
| Термины | ❌ | Нет. |
| Взаимосвязи между объектами | 🟡 | Есть связи вопрос → тема, цель, медиа и тема → подтема. Связей предметной области (художник → направление → период) нет. |
| Уникальный идентификатор | ✅ | UUID у всех объектов. |
| Унифицированный формат заданий | ✅ | Единый документ вопроса (stem, options, content, answerKey, feedback) и типы-конфигурации поверх плагинов (ADR-001). |
| Перенос между системами без потери структуры | ❌ / 🟡 | Экспорта нет; модель хорошо ложится на QTI (см. `docs/qti-readiness-audit.md`). |
| Независимость контента от платформы | 🟡 | Контент хранится как данные (JSON и версии), а не как код. Но формат проприетарный. |
| Решение по формату (QTI) | 🟡 | BRD откладывает решение до ТЗ. В проекте QTI вне MVP, ADR о формате обмена нет. |

**Рекомендация:** ввести справочник «Объект искусства» (Artwork, Artist, Movement, Period, Term) со связями и привязывать к нему медиа и вопросы. Это ключевой шаг для BRD 10.2, 10.9 и A.1; он затрагивает модель данных, поэтому лучше сделать его раньше.

### 10.3 Организация структуры курса — ✅/🟡

| Требование | Статус | Факт |
|---|---|---|
| Иерархия от блоков к заданиям | ✅ | Предмет → Курс → Тема → подтема (любая глубина) → вопросы и тесты. Иерархия «Раздел → Период → Тема» строится вложенными темами. |
| Привязка объектов и заданий к уровням | ✅ | Вопросы к темам и учебным целям, задания и тесты к курсу. Фильтр по теме учитывает подтемы. |
| Изменение структуры без разработчиков | ✅ | Через админку; права есть у преподавателя и администратора. |
| Типизированные уровни (раздел, период) | 🟡 | Уровни не типизированы: все узлы — «тема». Может понадобиться, когда в ТЗ будет зафиксирована модель структуры. |

Термин «задание» в BRD и в системе означает разное. В BRD задание — это учебное упражнение для студента; в системе это Item, «вопрос». Сущность Assignment («задание») означает поручение студенту подготовить тест. **Рекомендация:** выровнять глоссарий (приложение B) с `docs/domain-model.md`.

### 10.4 Выполнение учебных заданий — 🟡 (контент есть, выполнения нет)

Студент пока не может **выполнять** задания: прохождение реализовано только как модель (BL-12, без UI). Покрытие типов на уровне контента:

| Тип по BRD | Статус | Чем покрывается |
|---|---|---|
| Выбор правильного ответа | ✅ | `single_choice`, `true_false` |
| Выбор нескольких ответов | ✅ | `multiple_choice` |
| Установление соответствий | ✅ | `matching` |
| Распределение по категориям | ❌ | Плагина нет. Нужен тип классификации: несколько объектов в несколько групп (QTI `associate`/`gapMatch`). |
| Определение автора | ✅ | `attribution` |
| Определение направления | 🟡 | Через `attribution` или `single_choice` с изображением, отдельного типа нет; достаточно конфигурации. |
| Определение периода | 🟡 | Так же; дополнительно есть `chronology` (порядок). |
| Сравнение произведений | 🟡 | `image_choice` или вопрос с несколькими стимулами. Специального интерфейса сравнения (два изображения рядом) нет. |
| Работа с фрагментами изображений | ❌ | Нет hotspot (выбор области) и нет фрагмента как стимула (кроп). |

Сверх BRD реализованы `chronology`, `short_answer`, `essay`.

### 10.5 Индивидуальная траектория — ❌

Нет. Для нее нужны попытки и результаты студента: модель `attempts`/`results` в БД есть, но интерфейса прохождения нет. Нужен также алгоритм. Основа есть: метаданные вопросов (темы, цели, сложность) и правила случайного отбора по фильтру.

### 10.6 Система повторения — ❌

Нет. Алгоритм по BRD определяется отдельным методическим документом; его нет.

### 10.7 Обратная связь — 🟡

| Требование | Статус | Факт |
|---|---|---|
| Правильность ответа | 🟡 | Оценивание реализовано в плагинах (`evaluators`) и покрыто тестами, но студенту не показывается: нет прохождения. |
| Правильный ответ | 🟡 | Хранится (`answerKey`); в настройках теста есть режим показа правильных ответов. |
| Краткое объяснение | ✅ (данные) | Поле «Пояснение» (feedback) у вопроса. |
| Рекомендации по изучению | ❌ | Нет; можно вывести из связи вопрос → тема, цель. |

### 10.8 Отображение прогресса — ❌

Нет ни одного из пяти показателей.

### 10.9 Поиск и навигация — 🟡

Есть поиск по формулировке вопроса, по медиатеке (название, автор, теги), фильтры по теме, сложности и состоянию; p95 ≤ 700 мс на 50 000 вопросов. Поиска по художникам, произведениям, направлениям, периодам и терминам как по объектам нет: таких сущностей нет (см. 10.2).

|---|---|

| Управление ролями | ✅ (включая пользовательские роли) |
| Создание и редактирование контента | ✅ (вопросы, тесты, медиа, типы вопросов) |
| Управление структурой курса | ✅ |
| Публикация новых материалов | ✅ (версии, экспертиза, публикация и отзыв) |

## 5. Сильные стороны относительно BRD

- Процесс методической и редакторской проверки (BRD 14.3, 14.4, этап 4): экспертиза с чек-листами, блокирующими замечаниями, переносом замечаний между версиями.
- Неизменяемые версии контента и журнал аудита. Опубликованное нельзя изменить незаметно.
- Учет прав на изображения (BRD 13) встроен в процесс.
- Расширяемые типы заданий без программирования (BRD 11.4, 11.7).
- Оценивание и модель прохождения готовы как основа для 10.4 и 10.7.
