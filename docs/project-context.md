## 1. Цель проекта

Создать административную систему для **подготовки, экспертизы, публикации и управления тестами по искусству**
(история искусства, атрибуция произведений, стили, техники, иконография и т.п.).

Система — рабочая среда для трех групп людей:

* **студенты** создают вопросы и тесты в рамках учебных заданий (это форма обучения: составление теста — учебная задача);
* **преподаватели и эксперты** выдают задания, проверяют и принимают содержимое;
* **администраторы** управляют пользователями, правами, типами вопросов и публикацией.

Результат работы системы — **утвержденные, неизменяемые, опубликованные версии тестов**, пригодные для последующего
прохождения студентами (Student Runner) и для аналитики результатов.

## 2. Границы MVP

### Входит в MVP

| Блок | Содержание |
|---|---|
| BL-01 Identity & Authentication | вход, выход, сессии, пароли, статусы аккаунтов |
| BL-02 Roles & Permissions | RBAC + scope + ownership, server-side авторизация |
| BL-03 Educational Structure | предметы, курсы, темы/подтемы, учебные цели, группы студентов |
| BL-04 Assignments | задания студентам на создание тестов |
| BL-05 Media Library | изображения/видео, метаданные, права, alt text |
| BL-06 Question Type Registry | реестр типов вопросов, schema, конфигурация |
| BL-07 Item Bank | банк вопросов с версиями |
| BL-08 Test Authoring | тесты, версии, разделы, фиксированные и случайные вопросы, настройки |
| BL-09 Review Workflow | экспертиза, checklist, комментарии, замечания, решения |
| BL-10 Publishing & Lifecycle | жизненный цикл версий, публикация, отзыв |
| BL-11 Audit & Governance | журнал аудита, история, архив/восстановление |
| BL-12 Assessment Delivery Preparation | **только модель данных** Attempt/Response/Result |

### Сознательно НЕ входит в MVP

* Student Runner — интерфейс прохождения теста студентом (архитектура его учитывает, см. BL-12, `docs/assessment-model.md`).
* Вычисление аналитики (ItemStatistics, TestStatistics) — только зарезервированная модель.
* SSO / OIDC / LDAP — архитектурно предусмотрено (ADR-006), не реализуется.
* Consensus approval (несколько экспертов с обязательным согласием) — модель допускает, MVP использует одного primary reviewer.
* Создание новых interaction-типов через UI (только через код-плагины, ADR-001).
* Аудио-медиа, 3D, внешние IIIF-источники.
* Ручная оценка развернутых ответов (essay grading UI) — только модель `ResponseEvaluation` с методом `manual`.
* Мультиязычный контент (i18n контента). Интерфейс — на русском, архитектура не должна мешать локализации.
* Импорт/экспорт QTI.
* Публичный (неавторизованный) доступ к чему-либо.

## 3. Технологические ограничения

| Ограничение | Обоснование |
|---|---|
| **AdminJS — обязательный административный framework** | Решение владельца продукта |
| Node.js (LTS) + TypeScript | Следствие AdminJS |
| Реляционная БД (PostgreSQL) | Транзакции, целостность ссылок, JSONB для schema-driven данных (ADR-005, ADR-008) |
| Бизнес-логика вне AdminJS/React | ADR-004 |
| Хранение файлов — отдельно от метаданных (object storage) | ADR-007 |

Конкретный стек фиксируется в ADR-008.

## 4. Основные роли

| Роль | Код | Кратко |
|---|---|---|
| Студент | `STUDENT` | Создает вопросы и тесты в рамках назначенных заданий, дорабатывает по замечаниям |
| Преподаватель | `TEACHER` | Ведет учебную структуру своих курсов, создает задания, проводит экспертизу, создает вопросы для банка |
| Эксперт | `EXPERT` | Проводит экспертизу назначенного ему контента; не управляет заданиями |
| Администратор | `ADMIN` | Полный доступ: пользователи, роли, типы вопросов, публикация, аудит |

Роли — это наборы permissions (ADR-003). Пользователь может иметь несколько ролей. Состав permissions
каждой роли — в `docs/permission-model.md`.

## 5. Ключевые архитектурные принципы

1. **Specification first.** Ни одна задача не реализуется без спецификации и трассировки.
2. **Domain first.** Схема БД выводится из доменной модели, а не наоборот.
3. **AdminJS — только UI-слой.** Правила живут в domain/application layer (ADR-004).
4. **Server-side authorization везде.** Скрытие кнопки в UI — не мера безопасности (NFR-SEC-001).
5. **Immutable versions.** Отправленные на экспертизу и утвержденные версии не изменяются (ADR-002).
6. **Pinning.** Тест ссылается на конкретные версии вопросов; попытка — на конкретную версию теста.
7. **Soft delete.** Используемый контент не удаляется физически (BR-005).
8. **Audit by default.** Каждое значимое изменение журналируется в той же транзакции (BR-035).
9. **Extensibility through registry + plugins.** Новые конфигурации типов вопросов — через админку,
   новые interaction — через код (ADR-001).
10. **Delivery-ready.** Модель контента не должна закрывать путь к Student Runner и аналитике.

## 6. Глоссарий (кратко)

Полный глоссарий — в `docs/domain-model.md`.

| Термин | Значение |
|---|---|
| Item | Вопрос как переиспользуемая единица банка (идентичность) |
| ItemVersion | Конкретная версия содержимого вопроса |
| Test | Тест как идентичность (название, владелец, задание) |
| TestVersion | Конкретная версия структуры и настроек теста |
| Assignment | Задание студентам: создать тест на заданную тему с ограничениями |
| Review | Экспертиза конкретной версии |
| Published assessment | `TestVersion` в состоянии `PUBLISHED` — то, что может проходить студент |
